当前项目完全可以满足使用，但是需要有一些升级：

## 增加用户注册、登录页面
当前是后台增加key然后前端输入key登录，我们需要做一个登录注册的页面，表单：邮箱、密码、二次密码、用户名、可选的手机号。注册自动登录并复用当下用户key的流程。建议增加验证码
## 协议页面
登录、注册都要勾选协议，要在后台系统设置增加一个md编辑器并内置一套内容
## 管理员
管理员可以默认当前输入key的授权，但是建议增加验证码
## 后台用户
增加用户列表，按登录时间、使用次数排序。顶部可以加个card 统计，累计注册、当日活跃、当日累计生图、累计生图等
## 用户用量
需要检查当前对话画图业务是否计算了所有正常账号的图片总量，这个是我们的关键，
我们要增加排队逻辑， 当画图请求达到量就要让每个用户每次请求排队，并在前端页面展示出正在排队的状态。因为我做的是免费生图，所以系统设置也需要设置每天每个用户最多能成功生成几张，还有就是要设置用户的图片最多保存服务时间，
我建议3-5天，这个需要根据存储动态处理，有可能是1天或者几个小时内

## 图片管理
目前用户只开放了对话画图菜单，我建议开放图片管理，里面只是当前用户的图片、统计他的数量和占用空间。目前系统是管理员看全部

## 实施状态（2026-08-13）

当前已在现有 User Key、Application Database、Image Task Queue 和 ImageStorageService 边界内落地第一版：

- 新增邮箱/密码注册与登录接口，注册必须确认协议，注册和密码登录返回兼容现有 Bearer User Key 的访问密钥；旧管理员/用户 key 登录保持兼容。
- 系统设置新增 `user_daily_image_limit` 与 `protocol_markdown`，协议可由管理员通过既有设置接口保存，公开协议读取接口为 `/auth/protocol`。
- 图片任务继续使用既有 `queued`/`running` 状态；用户提交任务时按其当日已成功图片数执行每日额度校验，图片资产通过 `ImageStorageService` 记录 `owner_id`。
- `/api/images` 对普通用户仅返回本人资产，管理员仍可查看全部；新增 `/api/auth/users/stats` 管理员统计接口。
- 登录页面提供用户登录、用户注册和管理员密钥登录三种模式；登录与注册均要求勾选协议，协议内容从 `/auth/protocol` 读取。
- 注册页面包含邮箱、密码、二次密码、用户名和可选手机号，注册成功后自动登录并进入现有 Studio。
- 设置页已提供每日成功生图上限、图片保留时间和协议 Markdown 编辑/预览；用户管理已从系统设置中独立为管理员侧栏菜单，页面保留原用户操作与统计，并展示注册邮箱、用户名、注册时间和最近登录时间。
- 成功生图用量持久化在 User Key 数据中；旧 Application Database 中缺少新字段的用户自动按 `0` 和空值兼容，无需删除数据库。
